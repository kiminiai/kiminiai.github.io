# IT 리터러시 1편: 웹 서비스는 어떻게 요청하고 응답할까?

> 이 글은 이어드림스쿨 IT 리터러시 수업 내용을 바탕으로, 웹 서비스가 동작하는 전체 흐름을 정리한 글이다.  
> 단순히 용어를 외우는 것이 아니라, 사용자가 웹페이지에서 버튼을 눌렀을 때 실제로 어떤 요청과 응답이 오가는지 이해하는 것을 목표로 한다.

---

## 1. 컴퓨터는 결국 0과 1을 이해한다

프로그래밍을 처음 배우면 Python, JavaScript, Java 같은 언어를 먼저 접한다.  
하지만 컴퓨터가 직접 이해하는 것은 사람이 작성한 코드가 아니라 `0`과 `1`로 이루어진 기계어이다.

사람이 작성한 코드는 다음 과정을 거쳐 컴퓨터가 이해할 수 있는 형태로 바뀐다.

```text
CODE 작성 → 인터프리터/컴파일러 → 기계어 번역 → 컴퓨터 인식
```

여기서 중요한 것은 `High Level Language`라는 표현이다.  
처음에는 “고차원적인 언어”라는 뜻처럼 느껴질 수 있지만, 실제로는 **사람이 이해하기 쉬운 언어**에 가깝다는 의미로 이해하는 것이 좋다.

반대로 `Low Level Language`는 기계에 더 가까운 언어이다.  
기계를 세밀하게 제어할 수 있고 속도 면에서 유리할 수 있지만, 작성하기 어렵고 실수하기 쉽다.  
그래서 사람이 더 편하게 개발할 수 있도록 Python 같은 고수준 언어가 등장했다.

---

## 2. 운영체제는 컴퓨터를 쉽게 다루게 해주는 시스템 소프트웨어다

운영체제는 컴퓨팅 기계를 쉽게 다루기 위한 시스템 소프트웨어이다.

대표적인 운영체제는 다음과 같다.

| 운영체제 | 사용 예시 |
|---|---|
| Windows | 일반 PC, 사무용 환경 |
| macOS | MacBook, 개발 환경 |
| Linux | 서버, 개발 환경 |
| iOS | iPhone |
| Android | Android 스마트폰 |

우리가 프로그램을 실행하거나, 파일을 저장하거나, 인터넷에 접속할 때 운영체제가 중간에서 하드웨어와 소프트웨어를 관리해준다.

---

## 3. 통신은 컴퓨터 간의 대화다

웹 서비스를 이해하려면 먼저 통신을 이해해야 한다.  
통신은 컴퓨터 간의 대화이다. 스마트폰도 하나의 컴퓨터로 볼 수 있으므로, 스마트폰 앱과 서버 사이의 대화도 통신이다.

웹 통신은 기본적으로 다음 구조를 가진다.

```text
1 요청(Request) → 1 응답(Response)
```

사용자가 웹페이지에서 버튼을 누르면 브라우저가 서버에 요청을 보낸다.  
서버는 요청을 처리한 뒤 결과를 응답으로 돌려준다.

![웹 애플리케이션 서버 기본 구조](/img/it-literacy/web-architecture.svg)

위 구조를 보면 웹 서비스는 단순히 화면 하나로 끝나는 것이 아니다.  
사용자가 보는 화면 뒤에는 웹 서버, 백엔드 코드, 데이터베이스가 함께 움직인다.

---

## 4. HTTP는 웹에서 통신하기 위한 약속이다

HTTP는 `HyperText Transfer Protocol`의 약자이다.  
처음에는 단어가 어렵게 느껴지지만, 핵심은 간단하다.

> HTTP는 웹에서 클라이언트와 서버가 데이터를 주고받기 위한 약속이다.

여기서 프로토콜은 통신 규칙을 의미한다.  
즉, 서로 다른 기기와 운영체제, 브라우저가 통신하려면 모두가 이해할 수 있는 공통 규칙이 필요하다. 그 역할을 하는 것이 HTTP이다.

HTTP를 사용하면 다음이 가능하다.

- 기기에 상관없이 통신할 수 있다.
- 운영체제와 관계없이 통신할 수 있다.
- 브라우저 종류와 관계없이 통신할 수 있다.

결국 HTTP는 웹 서비스에서 “어떤 방식으로 요청하고 응답할 것인가”를 정해둔 약속이다.

---

## 5. JSON, XML, 파싱

웹에서 데이터를 주고받을 때는 보통 일정한 형식으로 데이터를 표현한다.  
대표적인 형식이 JSON과 XML이다.

요즘 웹 API에서는 JSON을 많이 사용한다.

```json
{
  "name": "minseok",
  "age": 25,
  "job": "student"
}
```

이 데이터는 사람이 보기에도 어느 정도 이해할 수 있고, 프로그램도 쉽게 읽을 수 있다.

여기서 파싱은 문자열로 받은 데이터를 프로그램이 사용할 수 있는 구조로 해석하는 것을 말한다.  
예를 들어 서버에서 JSON 문자열을 받았을 때, 필요한 값만 꺼내 사용할 수 있도록 바꾸는 과정이 파싱이다.

```text
JSON 문자열 → 파싱 → 필요한 데이터 추출
```

---

## 6. Endpoint는 서버 기능에 접근하는 주소다

Endpoint는 서버의 특정 기능에 접근하기 위한 주소이다.

예를 들어 다음 주소가 있다고 하자.

```text
https://shop.com/orders
```

여기서 `/orders`는 주문 관련 기능을 가리키는 Endpoint로 볼 수 있다.

사용자는 단순히 웹페이지에서 주문 목록을 본다고 생각하지만, 실제로는 브라우저가 `/orders`라는 주소로 서버에 요청을 보내고 서버가 주문 데이터를 응답하는 구조이다.

---

## 7. HTTP 메서드: GET, POST, PUT, PATCH, DELETE

웹 서비스에서는 주소만 중요한 것이 아니다.  
같은 주소라도 어떤 동작을 원하는지에 따라 HTTP 메서드가 달라진다.

![HTTP 메서드와 CRUD 감각](/img/it-literacy/http-methods.svg)

| 메서드 | 역할 | 예시 |
|---|---|---|
| GET | 기존 정보를 조회 | 주문 목록 조회 |
| POST | 정보를 생성하거나 전달 | 새 주문 등록 |
| PUT | 전체 수정 | 주문 정보 전체 수정 |
| PATCH | 일부 수정 | 배송지 일부 수정 |
| DELETE | 삭제 | 주문 삭제 |

처음에는 `PUT`과 `PATCH`가 헷갈릴 수 있다.  
간단히 말하면 `PUT`은 전체 수정, `PATCH`는 일부 수정에 가까운 느낌으로 이해하면 된다.

---

## 8. 동기와 비동기

통신 방식에서는 동기와 비동기 개념도 중요하다.

![동기와 비동기 통신의 차이](/img/it-literacy/sync-async.svg)

동기는 요청 결과가 올 때까지 기다린 뒤 다음 작업을 진행하는 방식이다.  
반면 비동기는 요청을 보낸 뒤 응답이 오기 전에도 다른 작업을 계속할 수 있는 방식이다.

대표적인 비동기 예시는 다음과 같다.

- 페이지 이동 없이 댓글 작성
- SNS 좋아요 클릭
- 피드 새로고침
- 채팅 메시지 전송

사용자 입장에서는 화면이 멈추지 않고 자연스럽게 동작하기 때문에 비동기 방식이 많이 사용된다.

---

## 9. 프론트엔드와 백엔드

웹 서비스는 크게 프론트엔드와 백엔드로 나눌 수 있다.

프론트엔드는 사용자가 직접 보는 화면을 담당한다.  
버튼, 입력창, 표, 그래프, 페이지 레이아웃 등이 여기에 해당한다.

백엔드는 서버 측에서 동작하는 코드를 담당한다.  
데이터를 저장하고, 조회하고, 수정하고, 필요한 계산을 처리하는 비즈니스 로직이 백엔드에서 실행된다.

비즈니스 로직은 프로그램에서 데이터를 생성, 표시, 저장, 변경하는 핵심 규칙이라고 볼 수 있다.

예를 들어 쇼핑몰에서는 다음이 비즈니스 로직이다.

- 주문 금액 계산
- 할인 쿠폰 적용
- 재고 수량 변경
- 결제 결과 저장
- 배송 상태 업데이트

---

## 10. REST API는 주소와 기능을 약속한 방식이다

REST API는 약속된 주소, 즉 URI를 가지고 있고 각 주소에 기능을 연결해둔 방식이다.

쉽게 말하면 다음처럼 이해할 수 있다.

```text
GET /orders       → 주문 목록 조회
POST /orders      → 주문 생성
GET /orders/1     → 1번 주문 조회
PATCH /orders/1   → 1번 주문 일부 수정
DELETE /orders/1  → 1번 주문 삭제
```

REST API에서 중요한 것은 주소만 보는 것이 아니라, **주소와 HTTP 메서드를 함께 봐야 한다는 점**이다.

같은 `/orders` 주소라도 `GET`이면 조회이고, `POST`이면 생성이다.

---

## 11. URI와 URL의 차이

URI와 URL도 자주 헷갈리는 개념이다.

- URI: 서버에서 특정 리소스를 식별하는 식별자
- URL: 우리가 흔히 말하는 웹사이트 주소

URL은 URI의 한 종류로 이해할 수 있다.  
즉, URI가 더 큰 개념이고 URL은 그 안에 포함된다.

처음에는 이 차이를 너무 깊게 외우기보다 다음 정도로 이해하면 충분하다.

> URL은 실제 위치를 나타내는 주소이고, URI는 리소스를 식별하는 더 넓은 개념이다.

---

## 12. 데이터베이스는 저장, 검색, 수정, 삭제를 담당한다

데이터베이스의 기본 기능은 다음 네 가지이다.

| 기능 | 의미 |
|---|---|
| 저장 | 데이터를 새로 넣는다 |
| 검색 | 필요한 데이터를 찾는다 |
| 수정 | 기존 데이터를 변경한다 |
| 삭제 | 필요 없는 데이터를 지운다 |

웹 서비스에서 데이터베이스는 보통 다음 흐름으로 사용된다.

```text
웹 브라우저/스마트폰 → 서버 조회 요청 → DB Query 실행 → 조회 결과 전달
```

예를 들어 사용자가 마이페이지에 들어가면 브라우저는 서버에 사용자 정보를 요청한다.  
서버는 데이터베이스에 쿼리를 보내고, 데이터베이스는 조회 결과를 서버에 돌려준다.  
서버는 이 결과를 다시 브라우저에 응답한다.

---

## 13. 서버 오류는 왜 발생할까?

서버 오류는 클라이언트와 서버가 정상적으로 통신할 수 없는 상황이다.

대표적인 원인은 다음과 같다.

- 트래픽 과부하
- 백엔드 코드 버그
- 데이터베이스 접속 오류
- 외부 API 장애
- 서버 자원 부족

사용자는 단순히 “사이트가 안 열린다”고 느끼지만, 내부적으로는 웹 서버, 백엔드, 데이터베이스 중 어디에서 문제가 발생했는지 확인해야 한다.

---

## 14. 정리하며

이번 글에서는 웹 서비스가 어떻게 요청과 응답으로 동작하는지 정리했다.

핵심은 다음과 같다.

| 개념 | 정리 |
|---|---|
| 통신 | 컴퓨터 간의 요청과 응답 |
| HTTP | 웹에서 데이터를 주고받기 위한 약속 |
| Endpoint | 서버 기능에 접근하는 주소 |
| REST API | URI와 HTTP 메서드를 조합한 API 설계 방식 |
| 프론트엔드 | 사용자가 보는 화면 |
| 백엔드 | 서버에서 비즈니스 로직을 처리하는 영역 |
| 데이터베이스 | 데이터를 저장, 검색, 수정, 삭제하는 시스템 |

웹 서비스를 이해할 때는 용어를 따로 외우기보다 다음 흐름으로 이해하는 것이 좋다.

```text
사용자 행동 → HTTP 요청 → 서버 처리 → 데이터베이스 조회/수정 → HTTP 응답 → 화면 반영
```

이 흐름을 잡고 나면 REST API, 백엔드, 데이터베이스 같은 개념이 훨씬 자연스럽게 연결된다.
